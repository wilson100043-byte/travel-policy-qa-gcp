# 需求規格

本文件定義差旅報帳規定問答系統的目標使用情境與需求，作為雲端架構設計的依據。情境為假想的中小企業，所有規定文件均為虛構資料。

本專案只做架構設計與靜態驗證，不實際部署；因此設計以**正式企業環境的合理做法**為準，不以零成本為前提。

## 1. 使用情境

一間約 200 名員工的中小企業，員工出差前後需要查詢差旅報帳規定，例如住宿上限、交通費用、應附單據與送件期限。規定由管理部門維護，每年會改版，新舊版本需要明確區分。

目標是讓員工用自然的中文提問，即時取得有依據的答案，減少管理部門重複回答相同問題。

## 2. 使用者與角色

| 角色 | 人數 | 需要做的事 |
| --- | --- | --- |
| 一般員工 | 約 200 人 | 以公司帳號登入，提問與追問差旅規定 |
| 管理部門 | 2–3 人 | 上傳、更新規定文件 |
| 系統管理者 | 1–2 人 | 部署、監控、處理告警 |

## 3. 功能需求

| 編號 | 需求 |
| --- | --- |
| FR-1 | 員工可用中文提問，並在同一頁面追問。 |
| FR-2 | 回答須附上依據的文件名稱與章節。 |
| FR-3 | 只引用目前生效的規定；問到舊版規定時，說明只提供現行規定。 |
| FR-4 | 文件中找不到依據時，明確回答查無資料，不得自行編造金額、期限或例外。 |
| FR-5 | 管理部門上傳或更新規定文件後，系統自動重建索引，不需人工操作。 |
| FR-6 | 對話只保存在使用者的瀏覽器，重新整理後清除；伺服器不保存提問內容。 |

## 4. 非功能需求

| 編號 | 類別 | 需求 | 說明 |
| --- | --- | --- | --- |
| NFR-1 | 容量 | 尖峰時段（月底報帳期）支援 **25 位使用者同時提問**。 | 約員工總數的八分之一。 |
| NFR-2 | 回應速度 | **90% 的問題在 8 秒內**回答（AI 生成）；離線模式 3 秒內。 | AI 生成需呼叫模型，時間較長。 |
| NFR-3 | 冷啟動 | 上班時間第一位使用者不需等待服務啟動。 | 上班時間預先保留執行個體。 |
| NFR-4 | 可用性 | 上班時間可用，目標 **99.5%**（每月停機不超過約 3.6 小時）。 | 非關鍵系統，單一區域即可，不需跨區備援。 |
| NFR-5 | 資料更新 | 文件上傳後 **1 小時內**生效。 | 規定每月更新數次。 |
| NFR-6 | 資料量 | 文件可從 4 份成長到**數百份**，檢索效能不明顯下降。 | 檢索方式需能隨資料量擴充。 |
| NFR-7 | 存取控制 | 只限公司員工，以公司 Google 帳號登入並**強制兩步驟驗證**；不限制連線 IP。 | 差旅規定常在出差時查詢，採零信任做法：驗證身分而非連線地點。 |
| NFR-8 | 資料存放 | 文件、索引與執行環境存放在**台灣**（asia-east1）。 | 企業內部文件的資料落地要求。 |
| NFR-9 | 機密管理 | 程式不使用長期 API key；以服務帳號身分存取雲端服務。 | 降低金鑰外洩風險。 |
| NFR-10 | 監控 | 錯誤率升高或回應變慢時，通知系統管理者。 | |
| NFR-11 | 稽核 | 記錄誰在何時存取系統；**不記錄提問內容**。 | 兼顧稽核與員工隱私。 |
| NFR-12 | 資料還原 | 規定文件誤改時，可還原到先前版本。 | |
| NFR-13 | 權限分工 | 只有管理部門能上傳規定文件；一般員工只能提問。 | |
| NFR-14 | 成本 | 不追求零成本，但優先選用量計費的服務，避免閒置資源浪費。 | |

## 5. AI 模式

| 環境 | 模式 | 說明 |
| --- | --- | --- |
| 正式環境 | **Vertex AI 生成（預設）** | 以服務帳號驗證，不需 API key；負責 Embedding、追問改寫與生成回答。 |
| 本機開發、評審測試 | 離線模式 | 不連網、不需任何帳號，用於開發與自動測試。 |

## 6. 不在範圍內

- 報銷申請與進度查詢等交易功能。
- 依部門區分可查詢的文件（規定為全公司共用）。
- 跨區域備援與災難復原演練。
- 實際部署到 GCP。

## 7. 假設

- 公司使用 Google Workspace 帳號，且已屬於一個 Google Cloud 組織。
- 規定文件為 Markdown 格式，開頭標註標題與生效期間，內文以 `##` 分章節。
- 尖峰時段每位使用者約 30 秒提問一次。
