③ 一次提問在後端經過的步驟

  1. 瀏覽器送出 {question, history}。Pydantic 限制問題最多 1,000 字、history 最多 20 筆，後端只取最近 6 筆（3 輪）。
  2. 問題含有「舊版、去年、2025」等字眼時，直接回答「只提供現行規定」，不進行搜尋。
  3. load_index：GCS 模式下先讀取 processed/index.json 的 metadata。generation（GCS 的物件版本號）沒變就直接用記憶體快取，變了才重新下載，並檢查 schema 版本、模式和 Embedding 模型是否相符。
  4. 改寫追問：offline 模式用規則把上一題接到短追問前面；gemini 模式請模型改寫成可以單獨搜尋的問題。
  5. 搜尋：先用 effective_from／effective_to 濾掉非生效章節，再依 cosine 相似度取前 3 名（gemini 模式另設 0.35 門檻）。
  6. 回答：offline 抽出最相關的 2 句，只引用 1 個章節；gemini 模式只根據這 3 個章節生成，回「查無資料」時不附來源。
  7. 錯誤：Gemini 失敗時回 503 和中文說明；其他例外一律回通用訊息，不把雲端錯誤細節傳給前端。
來源：app/main.py、app/rag.py ask()、search()

② 建立索引的 Job 做什麼

  1. 列出 raw/ 下的 .md，解析開頭的 title、effective_from、effective_to。
  2. 依 ## 標題把文件切成章節（目前共 36 節）。
  3. offline：用中文字元 2–3 gram 計算 TF-IDF 向量，不需要外部服務。gemini：每個章節呼叫一次 embedContent（RETRIEVAL_DOCUMENT，768 維）。
  4. 整份結果寫成一個 JSON 檔，放到 processed/index.json，裡面記錄 schema_version、mode、embedding_model。
來源：app/indexer.py build_index()、app/documents.py parse_document()

① 部署順序：Terraform 為什麼分兩階段

  1. bootstrap：啟用 API、建立 bucket 並上傳 raw/、建立 Artifact Registry，以及一個沒有值的 secret。
  2. 手動：首次啟用 IAP 時，無組織的專案須先在 Console 完成 OAuth 設定。（選用）以 stdin 把 Gemini key 加進 Secret Manager；再用 gcloud builds submit 建立映像。
  3. app：建立兩個 service account、IAM 權限、Cloud Run Service 和 Job。這一步需要第 2 步產生的 image_uri。
  4. 手動執行一次 Job 產生索引，再開啟服務網址，以授權的 Google 帳號登入測試。

為什麼要分兩階段？Cloud Run 建立時映像必須已經存在，而金鑰的值不能寫進 Terraform state，所以中間一定有一段手動步驟。

來源：infra/bootstrap/main.tf、infra/app/main.tf、docs/DEPLOYMENT.md

④ 安全設計

  • 服務不公開：IAP 直接啟用於 Cloud Run，使用者須以名單內的 Google 帳號登入，未授權者在進入應用程式前即被拒絕。run.invoker 只授予 IAP 的服務代理，沒有授權給 allUsers。
  • 金鑰只放一處：不在 Git、tfvars、state、映像或網址裡，只存在 Secret Manager，執行時才注入成環境變數。
  • 最小權限：Service 和 Job 各用一個 SA。Job 的寫入權限用 IAM Condition 限制在 processed/ 前綴。
  • Bucket：uniform bucket-level access，並強制開啟公開存取防護。
  • 提示注入防護：prompt 要求模型只根據章節回答，不聽從文件裡要它改變規則的文字。
來源：infra/app/main.tf、app/gemini.py、app/rag.py _gemini_answer()

成本護欄

  • Service 最少 0、最多 1 個實例：閒置時不跑，流量大時也不會一直擴充。
  • Job 不排程、不重試，最長 600 秒。
  • 預設 offline，不呼叫 Gemini。要開 gemini 模式必須同時設定 ai_mode 和 gemini_free_tier_confirmed，Terraform precondition 會檢查。
  • 私人 repo 會跳過 CI，而且 CI 沒有任何部署權限。
  • 注意：Storage、Secret、Artifact Registry、Build、Logging 超出免費額度後仍會收費。

架構檢視：已處理項目與後續改進方向

已修正每次提問都重新下載索引

原本 ask() 每次都呼叫 load_index()，GCS 模式下每題都下載一次 index.json。現在改成快取在程序記憶體，只用一次 metadata 請求比對 generation，Job 寫入新索引後才重新下載。驗證索引失敗的版本不會被快取。（app/indexer.py _load_gcs_index()）

已修正gemini 模式的逾時加總超過 Cloud Run 上限

一題最多依序呼叫 Gemini 3 次（改寫、Embedding、生成）。原本每次逾時 25 秒，最壞 75 秒，超過 Service 的 60 秒 timeout。現在單次逾時改成 15 秒，最壞 45 秒；測試也會讀取 Terraform 設定，確認逾時總和低於 Service 上限。（app/gemini.py GEMINI_TIMEOUT_SECONDS）

取捨選 AI Studio API key，而不是 Vertex AI

Vertex AI 可以直接用 service account 驗證，完全不需要 API key，也就不需要 Secret Manager。這裡選 API key 是為了使用 AI Studio 的 Free Tier。若需正式環境或企業資料，建議改用 Vertex AI 以 service account 驗證。

建議其他可以提的改進

  • Terraform 目前是本機 state。多人協作時改用 GCS backend，才有狀態鎖和共享。
  • Secret 參照 latest：輪替金鑰後，要等新實例啟動才會拿到新值。正式環境可以改成固定版本。
  • Dockerfile 也 COPY policy_docs，但雲端實際讀的是 GCS，等於有兩份文件來源。可以拿掉，避免混淆。
  • 更新文件後要手動重跑 Job。可以用 Eventarc 監聽 raw/ 上傳後自動觸發。這次刻意不做，是為了避免產生費用。
