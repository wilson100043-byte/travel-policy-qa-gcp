③ 一次提問在後端經過的步驟

  1. 員工開啟網址，IAP 要求以公司 Google 帳號登入，確認在授權名單內才放行。
  2. 瀏覽器送出 {question, history}。問題最多 1,000 字，後端只取最近 6 則訊息（3 輪）。
  3. 問題含有「舊版、去年、2025」等字眼時，直接回答只提供現行規定。
  4. load_index：比對 processed/index.json 的版本號（generation），沒變就用記憶體快取。
  5. Vertex AI 把追問改寫成可單獨搜尋的問題，再轉成向量。
  6. 依 effective_from／effective_to 排除失效規定，取相似度最高的 3 個章節（低於 0.35 不採用）。
  7. Vertex AI 只根據這 3 個章節生成答案；找不到依據時回答查無資料，不附來源。
  8. 錯誤時回 503 與中文說明，不把雲端錯誤細節傳給前端。
來源：app/main.py、app/rag.py ask()、search()、app/vertex.py

② 自動建立索引

  1. 管理部門把規定上傳到 raw/，bucket 保留舊版本，改錯可以還原。
  2. Eventarc 收到上傳或刪除事件，啟動 Workflows。Eventarc 無法直接啟動 Job，也不能依路徑過濾，所以由 Workflows 確認檔案是 raw/*.md。
  3. Workflows 啟動 Cloud Run Job：解析標題與生效期間，依 ## 切章節。
  4. 每個章節呼叫 Vertex AI gemini-embedding-001 產生 768 維向量。
  5. 整份結果寫成 processed/index.json。Job 寫入 processed/ 也會產生事件，但 Workflows 會忽略，不會無限循環。
來源：infra/app/reindex.tf、reindex.workflow.yaml、app/indexer.py

① 部署順序

  1. bootstrap：啟用 API、建立 bucket（開啟版本保留）與 Artifact Registry。
  2. 建置：gcloud builds submit 建立映像，tag 不可覆寫。
  3. app：建立服務帳號與權限、Cloud Run Service 與 Job、IAP、自動索引、監控告警。
  4. 上傳規定：管理部門上傳到 raw/，自動產生索引。

為什麼分兩階段？Cloud Run 建立時映像必須已經存在，所以先建映像庫、建好映像，再建執行環境。

來源：infra/bootstrap/、infra/app/、docs/DEPLOYMENT.md

④ 安全與維運

  • 零信任登入：IAP 驗證公司帳號並強制兩步驟驗證，不限制連線地點，出差也能用。
  • 沒有長期金鑰：Service 與 Job 以服務帳號呼叫 Vertex AI，不需要 Secret Manager。
  • 最小權限：每個工作負載各用一個服務帳號；Job 只能寫 processed/，管理部門只能寫 raw/。
  • 監控：回應過慢、伺服器錯誤、索引失敗時寄信給系統管理者。
  • 稽核與隱私：記錄誰透過 IAP 存取；不記錄提問內容。
來源：infra/app/main.tf、monitoring.tf

已處理索引快取與逾時預算

索引依 Cloud Storage 的版本號快取，不再每題下載；AI 單次逾時 15 秒，三次呼叫共 45 秒，低於 Cloud Run 的 60 秒上限，並有測試檢查兩邊設定。

已處理依需求重新設計

容量改為 1–5 個實例、每個併發 10；文件與執行環境移到台灣；改用 Vertex AI，不再使用 API key；上傳後自動重建索引；加入監控、稽核與版本保留；Terraform 不再覆蓋管理部門上傳的規定。

取捨AI 推論在美國處理

官方文件沒有列出台灣提供所需的 Gemini 模型，所以只採用官方明確確認可用的組合：生成用 gemini-3.5-flash-lite（us 多區域），Embedding 用 gemini-embedding-001（us-central1）。文件、索引與執行環境仍留在台灣；官方日後列出台灣或鄰近區域時，只要調整兩個 Terraform 變數。

其他限制

  • 短時間上傳多個檔案時，每個檔案都會啟動一次 Job，會重複執行；只由讀到最新文件的那次寫入索引。
  • Cloud Monitoring 沒有第 90 百分位，回應告警用第 95 百分位、8 秒，比需求略嚴格。
  • IAM、Eventarc 與告警只通過靜態檢查，實際行為要部署後驗證。
